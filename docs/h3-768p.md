# MiniMax H3 — 768p mode and the Flex recipe

Resolution options for H3 workflows: **480p**, **ESRGAN 2x** (stored value `720p`, unchanged) and
**768p** (new, native two-stage). 768p costs **2x credits** and is an advanced-features option like 720p.

## What 768p does
`src/lib/h3TwoStage.ts` rewrites the finished single-stage H3 graph into the validated two-stage layout:
low-res (half the edges, e.g. 672x384) over the first part of the sigma schedule -> `MiniMaxH3LatentUpscaleWithModel`
on stage 1's `denoised_output` -> high-res (1344x768) over the rest, with fresh noise at the switch sigma.

| Family | Template sigma source | Split |
|---|---|---|
| Official H3 — Pika Flex rows | `ManualSigmas` 6 steps, lcm | 3 + 3 |
| Official H3 — turbo rows, Singularity / Dasiwa hybrids | `BasicScheduler` 8 steps, euler | 6 + 2 (`SplitSigmas`) |

Same-seed L40S comparison (official ref2va pruned, kung-fu mannequin 6s, ref video 144 frames, sage on): Flex 3+3 172.7s,
turbo 6+2 171.4s, turbo 480p 123.0s — 6+2 is not slower than 3+3.

Each stage gets its own sigma-shift / sage-patch chain (as in the validated graphs). No extra duration cap: 15s was
validated on the L40S (Flex 3+3, 491s); 15s on serverless is untested (extrapolated ~14 min vs the 30 min endpoint timeout).

## Flex templates (official H3 only)
`data/minimax_ref2v_flex.json.tmpl` (ref2va pruned) and `data/minimax_h3_flex.json.tmpl` (fl2va pruned): `ManualSigmas`
(6 steps), `lcm`, CFG 1 `BasicGuider`, no `MiniMaxH3SigmaShift`, no `BasicScheduler`. The Flex recipe is the LoRA +
sigmas + sampler together, which is why these are separate templates.

**No recipe special case for the LoRA.** The templates contain no LoRA node: the builders inject the workflow's
required LoRA (admin preset with `isConfigurable=false`) after the UNETLoader exactly like the turbo speed-up LoRA —
for Flex that required preset is `pika_h3_flex_ref2va_v1_bf16` / `pika_h3_flex_fl2va_v1_bf16`. Steps are only
rewritten when a `BasicScheduler` drives the schedule (turbo templates); Flex carries its own `ManualSigmas`.
A Flex row without a required LoRA would run the plain base model (not defended in code — configure the row).
(`/data` is git-ignored; the tracked templates are force-added.)

## Style LoRAs (all H3 rows)
The worker never edits workflows; the site sends them fully wired. `src/lib/h3StyleLoras.ts` chains the enabled
non-required presets (present in `loraWeights`, compatible with the workflow) after the required LoRA and before the
sigma-shift / sage patch. Before this the H3 builders only applied the required LoRA, so UI selections had no effect.

## Worker requirements
- ComfyUI with `MiniMaxH3LatentUpscaleWithModel` (PR #17412), `comfy-kitchen >= 0.2.40`, and
  `models/latent_upscale_models/minimax_h3_latent_upscaler_3d_fp16_V2.safetensors`.
- Sage attention workers get one `MiniMaxH3MemoryEfficientSageAttentionPatch` per stage (existing `useSageAttention`
  mechanism). **Without the patch on a sage worker long clips turn to noise** — never skip it there.
- Local workers: declare `h3_latent_upscale` in `x-worker-capabilities`, or (undeclared workers, e.g. the L40S)
  set `ENABLE_H3_TWO_STAGE_LOCAL=true` on the site. Default is off: workers without it are never handed a 768p job
  (`claimLocalJob(userId, { allowH3TwoStage })`). RunPod serverless needs image >= GmComfy `51bbae4`.

## Enabling it (DB, nothing runs automatically) — workflow rows
Decision (duo, 2026-10-31): keep BOTH official H3 flavours so users choose, and make **Pika Flex the DB default for r2v, i2v and fl2v**
(the default statement runs after deployment; the site code handles both flavours before and after the switch).
So the Flex workflows are **new rows**; the existing turbo rows stay and only gain 768p (6+2).
Capabilities are opt-in per workflow row (kickoff rejects a resolution not in `capabilities.resolutions`). The admin workflow form
has a resolution toggle (480p/720p/768p) and sends the row's `resolutions`/`durations` back on save, so editing a row no longer drops 768p.

Both `capabilities` and `quota_cost_rules` are MERGED, never overwritten: other rules on the row
(ref-video surcharge, duration tiers, custom `durations`/`freeSteps`) must survive. The rule id
`res-768p` is replaced in place, so re-running these statements is idempotent.

**0. LoRA presets, first** (they live in `admin_settings.lora_presets`; saving presets in the admin UI purges workflow LoRA ids
that have no preset, so they must exist before the workflow rows below). Either add them in the admin UI, or run the idempotent
statement at the top of the SQL block (`isConfigurable=false`, `chain: high`, default 1):
`pika_h3_flex_ref2va_v1_bf16.safetensors`, `pika_h3_flex_fl2va_v1_bf16.safetensors`, and (if the DB lacks it)
`minimax_h3_ref2v_turbo_8step_v1.0_768p_comfyui_bf16.safetensors`. Do not remove the turbo presets — the turbo rows keep using them.

```sql
-- 0. LoRA presets (admin_settings.lora_presets is a JSON array; the admin UI edits the same thing). Run FIRST.
--    Idempotent: only appends ids that are not already defined. Presets must exist before the workflow rows reference
--    them, because saving presets in the admin UI purges workflow LoRA ids that have no preset.
--    The turbo ref2v 8-step 768p preset is included for DBs that do not have it yet (already present on production = skipped).
UPDATE admin_settings
SET lora_presets = COALESCE(lora_presets, '[]'::jsonb) || (
  SELECT COALESCE(jsonb_agg(p), '[]'::jsonb)
  FROM jsonb_array_elements($j$[
    {"id":"minimax_h3_ref2v_turbo_8step_v1.0_768p_comfyui_bf16.safetensors","label":"Light X2V Ref2VA Turbo (8-step, 768p)","default":1,"min":0,"max":1.5,"step":0.05,"isConfigurable":false,"defaultEnabled":true,"tags":["lightx2v"],"presetGroup":"minimax","autoAddToWorkflows":false},
    {"id":"pika_h3_flex_ref2va_v1_bf16.safetensors","label":"Pika H3 Flex Ref2VA (6-step)","default":1,"min":0,"max":1.5,"step":0.05,"chain":"high","isConfigurable":false,"defaultEnabled":true,"tags":["pika"],"presetGroup":"minimax","autoAddToWorkflows":false},
    {"id":"pika_h3_flex_fl2va_v1_bf16.safetensors","label":"Pika H3 Flex FL2VA (6-step)","default":1,"min":0,"max":1.5,"step":0.05,"chain":"high","isConfigurable":false,"defaultEnabled":true,"tags":["pika"],"presetGroup":"minimax","autoAddToWorkflows":false}
  ]$j$::jsonb) p
  WHERE NOT EXISTS (
    SELECT 1 FROM jsonb_array_elements(COALESCE(admin_settings.lora_presets, '[]'::jsonb)) e WHERE e->>'id' = p->>'id'
  )
)
WHERE id = 'default';

-- 1. Existing turbo rows (official H3, Singularity, Dasiwa): add 768p (6+2) and the x2 rule; steps/LoRAs unchanged
UPDATE workflows
SET capabilities = COALESCE(capabilities, '{}'::jsonb) || '{"resolutions":["480p","720p","768p"]}'::jsonb,
    quota_cost_rules = (
      SELECT COALESCE(jsonb_agg(r), '[]'::jsonb)
      FROM jsonb_array_elements(COALESCE(quota_cost_rules, '[]'::jsonb)) r
      WHERE r->>'id' IS DISTINCT FROM 'res-768p'
    ) || '[{"id":"res-768p","label":"768p x2","multiplier":2,"when":{"exactResolution":"768p"}}]'::jsonb
WHERE id IN ('minimax-h3','minimax-h3-fl2v','minimax-h3-r2v',
             'singularity-h3','singularity-h3-fl2v','singularity-h3-r2v',
             'dasiwa-h3','dasiwa-h3-fl2v','dasiwa-h3-r2v');

-- 2. New Pika Flex rows, cloned from the official turbo rows (same quota_cost, tags, preset group, run_on, style LoRAs;
--    the turbo LoRA id is swapped for the Flex one; 6 fixed steps; 480p / ESRGAN 2x / 768p). Re-runnable: skips existing ids.
INSERT INTO workflows (id, name, description, "templatePath", compatible_lora_ids, is_default, created_at, updated_at,
                       workflow_type, is_deleted, auto_include_new_loras, preset_group, tags, quota_cost,
                       quota_cost_rules, engine, run_on, capabilities)
SELECT n.new_id, n.new_name, n.new_desc, n.tmpl,
       (w.compatible_lora_ids - n.turbo_lora) || to_jsonb(ARRAY[n.flex_lora]),
       false, now(), now(), w.workflow_type, false, w.auto_include_new_loras, w.preset_group, w.tags, w.quota_cost,
       '[{"id":"res-768p","label":"768p x2","multiplier":2,"when":{"exactResolution":"768p"}}]'::jsonb,
       w.engine, w.run_on,
       '{"steps":[6],"freeSteps":6,"resolutions":["480p","720p","768p"]}'::jsonb
FROM (VALUES
  ('minimax-h3-r2v',  'minimax-h3-pika-r2v', 'Minimax H3 R2V (Pika Flex)', '海螺3.0 参考生视频 · Pika Flex 6 步',
     'data/minimax_ref2v_flex.json.tmpl', 'minimax_h3_ref2v_turbo_8step_v1.0_768p_comfyui_bf16.safetensors', 'pika_h3_flex_ref2va_v1_bf16.safetensors'),
  ('minimax-h3',      'minimax-h3-pika',     'Minimax H3 (Pika Flex)',     '海螺3.0 多模态 · Pika Flex 6 步',
     'data/minimax_h3_flex.json.tmpl',    'minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors',      'pika_h3_flex_fl2va_v1_bf16.safetensors'),
  ('minimax-h3-fl2v', 'minimax-h3-pika-fl2v','Minimax H3 FL2V (Pika Flex)','海螺3.0 首尾帧 · Pika Flex 6 步',
     'data/minimax_h3_flex.json.tmpl',    'minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors',      'pika_h3_flex_fl2va_v1_bf16.safetensors')
) AS n(src_id, new_id, new_name, new_desc, tmpl, turbo_lora, flex_lora)
JOIN workflows w ON w.id = n.src_id
WHERE NOT EXISTS (SELECT 1 FROM workflows x WHERE x.id = n.new_id);

-- 3. Default = Pika Flex, for all three types (RUN AFTER the new code is deployed). is_default is per workflow_type
--    (getDefaultWorkflow(type) picks the one default per type for new entries and for jobs without a workflow_id).
--    This unsets the current i2v / fl2v defaults (the Wan Dasiwa v9 rows) and the turbo ref2v default.
UPDATE workflows
SET is_default = (id = CASE workflow_type WHEN 'ref2v' THEN 'minimax-h3-pika-r2v'
                                          WHEN 'i2v'   THEN 'minimax-h3-pika'
                                          WHEN 'fl2v'  THEN 'minimax-h3-pika-fl2v' END)
WHERE workflow_type IN ('ref2v', 'i2v', 'fl2v') AND is_deleted = false;

-- 4. (optional) tell the two flavours apart in the dropdown
UPDATE workflows SET name = 'Minimax H3 R2V (Turbo)' WHERE id = 'minimax-h3-r2v' AND name = 'Minimax H3 R2V';
UPDATE workflows SET name = 'Minimax H3 (Turbo)'     WHERE id = 'minimax-h3'     AND name = 'Minimax H3';
UPDATE workflows SET name = 'Minimax H3 FL2V (Turbo)' WHERE id = 'minimax-h3-fl2v' AND name = 'Minimax H3 FL2V';

-- 5. Native Wan 720p ('720p-hd', generated at 1280x720-class, x2 credits at 4s, x3 from 6s). Opt-in per row: this applies to ALL
--    non-deleted Wan rows; narrow it with `AND id IN (...)` to offer it on selected models only. Merge, idempotent; the ESRGAN
--    rule/id '720p' is untouched. Two stacked rules: x2, and x1.5 more when duration >= 6 (= x3; the final credit is rounded to an integer).
UPDATE workflows
SET capabilities = COALESCE(capabilities, '{}'::jsonb) || jsonb_build_object('resolutions',
      CASE WHEN COALESCE(capabilities->'resolutions', '[]'::jsonb) @> '"720p-hd"'::jsonb
           THEN capabilities->'resolutions'
           ELSE COALESCE(capabilities->'resolutions', '["480p","720p"]'::jsonb) || '"720p-hd"'::jsonb END),
    quota_cost_rules = (
      SELECT COALESCE(jsonb_agg(r), '[]'::jsonb)
      FROM jsonb_array_elements(COALESCE(quota_cost_rules, '[]'::jsonb)) r
      WHERE r->>'id' IS NULL OR r->>'id' NOT IN ('res-720p-hd', 'res-720p-hd-long')
    ) || '[{"id":"res-720p-hd","label":"720p native x2","multiplier":2,"when":{"exactResolution":"720p-hd"}},
           {"id":"res-720p-hd-long","label":"720p native, 6s+ (x3 total)","multiplier":1.5,"when":{"exactResolution":"720p-hd","minDuration":6}}]'::jsonb
WHERE engine = 'wan' AND is_deleted = false;
```
Rollback: set `is_deleted = true` on the three `minimax-h3-pika*` rows (hides them) and `is_default = true` on
the previous defaults (`minimax-h3-r2v`, `dasiwa-v9`, `dasiwa-v9-fl2v`); the turbo rows were never touched apart from the additive 768p capability/rule.

Note: the tracked `data/minimax_ref2v_template.json.tmpl` (turbo, official r2v) now points at the pruned base,
matching the live working tree — `git checkout` the live copy before pulling this branch.

## Native Wan 720p and the ESRGAN rename (2026-11-01)
Resolution ids are unchanged so stored rows, quota rules and in-flight jobs keep working; only the meaning/labels moved:
`720p` = the ESRGAN route (480p render, upscaled 2x; shown as "ESRGAN 2×"), new `720p-hd` = native Wan 720p
(generated at 1280x720 / 720x1280, the official Wan 2.2 720p budget of 921,600 px; shown as "720p"), `768p` = H3 two-stage.
`720p-hd` is Wan-only (kickoff rejects it on H3), opt-in per row via `capabilities.resolutions`, premium like the other
non-480p options, and costs **x2 at 4s and x3 from 6s** (two stacked rules, `res-720p-hd` x2 and `res-720p-hd-long` x1.5 with
`minDuration: 6`; credits are rounded to an integer; relay mode maps its frame total to 4s/6s/10s: <=81 / <=121 / more). Step 5 of the SQL.
Measured 720p-hd vs 480p exec time, L40S, same seed/image, 4-step Wan 2.2 with sage (single samples, +-15% noise between repeats of the same job):
81 frames 2.03x (plana) / 2.34x (arona); 121 frames 2.6-3.0x (480p 77.2 s and 89.1 s, 720p-hd 230.6 s); relay 177 frames about 3.0-3.2x
(408.5 s vs 128.9 s, 720p-hd ran first so it includes cold model load). Non-relay Wan tops out at 121 frames; 177 only exists in relay mode.
Not yet run on RunPod serverless (MIG, no sage): check VRAM/time there first.

## Verified (2026-10-30, 6s unless noted; single sample, white-mannequin / portrait first frame)

  Dasiwa 6+2 158s (480p 122s); Singularity 6+2 124s (480p 95s); two-person swap r2v with 2 refs + ref video + audio 200s.

- Not validated: Singularity i2v (motion_enhancer) and Dasiwa i2v/fl2v at 768p, 10s/15s on serverless,
  fl2v with a last frame, Flex stacked with style LoRAs (H3 builders only inject the speed-up LoRA anyway).
